## 2026.10.15 - The interned id is namespaced: a whole-genotype constant no longer takes its genotype node's id

**The defect.** `constant_id(payload)` was `sha256(payload)`, and a whole-genotype constant's payload is `json.dumps(genotype.model_dump())`, the same bytes `CellAdapter._genotype_node`, `_segregant_genotype_node_from` and `_perturbed_segregant_genotype_node_from` hash for the node id. `FastCsvSink` deduplicates node ids in one set across every label, and every adapter conf runs `experiment (chunked)` before the genotype node methods, so the `interned constant` row owned the id and the genotype node row was dropped without a word. The CSV endpoint gate of 2026-10-15 checked only that an endpoint names SOME node, which such an id does.

**Measured on the job 4901 partial** (`/db/database/biocypher-out/2026-10-14_03-53-33`, read-only; [[experiments.database.scripts.interned_id_collision_counts]], 133 s): 242,984 `InternedConstant` rows, of which 218,258 are kind `genotype` and 135 kind `genotype.background`; none of those 218,393 ids is in a genotype node file. Edge rows landing on an interned-only id: `GenotypeMemberOf` 1,948,098 of 95,910,118 (218,258 distinct genotypes), `PerturbationMemberOf` 121,180 of 47,251,386 (121,143 distinct), `SegregantBackgroundOf` 709,716 of 894,907 (the 135 backgrounds). Per dataset (genotype nodes lost): CrispriSegregantHale2024 121,140 (its 35 backgrounds under 8,192 bytes leave the top-level rule in charge, which interns the whole perturbed segregant genotype), Boocock2025 79,443, Bloom2019 13,720, Nguessan2025 2,948, IsolateGrowthPeter2018 971, CaudalPanTranscriptome2024 943, the three DeChiara2022 leaves 906, 906 and 905, ProteomeMuenzner2024 794, ProteinTurnoverMuenzner2024 55, the four Brunk2016 leaves 2 each (the same two genotypes), GrowthRateChoe2019 1. The reverse direction is clean: all 1,948,098 whole-genotype pointers and 6,629,132 background pointers in the Experiment blobs resolve to an interned constant, so the query loader never saw it; the graph side did. Lane H's 121,237 `PerturbationMemberOf` rows is the same set counted once per dataset (the four Brunk leaves share their 19 rows); counted once per row it is 121,180.

**Measured on the served KG 3.0 store** (`tc-neo4j-readonly`, bolt, read transactions only; [[experiments.database.scripts.interned_id_collision_served]], 8 s): 21,020 `InternedConstant` nodes, 14,573 of kind `genotype`; 518,883 of 52,668,931 `GenotypeMemberOf` relationships start at an `InternedConstant` instead of a genotype node: Bloom2019Dataset 13,630 genotypes (517,940 rows; 320 of its segregant genotypes survive as `SegregantGenotype` nodes) and CaudalPanTranscriptome2024Dataset 943 genotypes (943 rows). `PerturbationMemberOf` is untouched there (0 of 45,297,656), and all 941 sampled blob pointers resolve. KG 3.0 (commit `4b293d34`, 2026-10-06) was built after interning landed (r9, 2026-09-28), so the data served today carries the defect; the 4.0 release note states it.

**The fix.** `constant_id(kind, payload)` hashes the label, a NUL byte, the kind, a NUL byte and the payload. Every other content id hashes a JSON document (first byte `{`), so the preimages are disjoint by construction. The kind is in the preimage because the same `SegregantGenotype` bytes can be a whole `genotype` in one dataset and a `genotype.background` in another, and the node's `kind` property has to be true of the node rather than of whichever record wrote it first; under payload-only addressing the array merge would also refuse the two differing rows. `verified_constant(ref, kind, payload)` recomputes the id from the node's own two properties, and `Neo4jQueryRaw.fetch_constants` now fetches `n.kind` with the payload. The Experiment node id is unchanged (still the sha256 of the inlined record), the genotype node ids are unchanged; only the interned ids and the `$ref` values in the blobs move, which the 4.0 full rebuild absorbs.

**Alternatives weighed.** Per-label dedup in the sink: not available, `neo4j-admin import` has one id space and `--skip-duplicate-nodes=true` keeps the first row of an id whatever its label, so two nodes with one id cannot be imported; it would only move the drop from the sink into the import. Not interning whole genotypes: removes this instance and leaves the mechanism (the `genotype.background` constant collides with the `SegregantGenotype` node the same way, and any future interned field whose node hashes the bare dump would too), and puts tens of KB of haplotype blocks back into every Bloom, Boocock and Hale blob. Namespacing is the one that makes the collision impossible rather than unlikely, and it costs nothing the rebuild is not paying already.

**Guards.** `FastCsvSink` and `RenderedChunk.from_rows` now keep `id -> label` and raise on an id arriving under a second label ([[torchcell.fast_csv]]); the CSV endpoint gate checks every endpoint's label against the schema yaml and every node id against a second label ([[torchcell.knowledge_graphs.csv_endpoint_gate]]). Regression tests: `tests/torchcell/adapters/test_interned_id_collision.py` (a synthetic fitness record with 48 deletions, above the 8,192-byte floor, through the adapter's methods, the chunk renderer and the sink in method order; on the old `constant_id` the constant's id equals the genotype node's id and the `Genotype` row is not written), `test_an_id_under_a_second_label_is_refused_not_dropped` in `tests/torchcell/test_fast_csv.py`, and the label-gap, ancestry and collision tests in `tests/torchcell/knowledge_graphs/test_csv_endpoint_gate.py`. No schema-change record: `schema.py` and `pydant.py` are untouched and no served pydantic closure changes; `python -m torchcell.provenance.schema_change check` passes as before (Rule 8).
