## 2026.10.10 - Every mapped store verified against the bytes on disk before KG 4.0

`build_dataset_lmdb` builds a store and does not verify it. Slurm array 3565 rebuilt 105
dev stores from `main` on 2026.10.09, and `--list-stale --include-private` then read 0. That
gate compares schema-closure fingerprints and never asks whether the records still satisfy
their own L0 to L4 rules. Measured before this sweep: 115 of the then 123 mapped stores

`gene_interaction_butland2008`, `growth_rate_lamoureux2023`, `growth_rate_s23_schmidt2016`,

### Three routes, and the route is a property of the dataset

| Route | Datasets | What owns the battery |
|---|---:|---|
| `module` | 48 | the loader module's own entry point (`run_verification`, `verify_build`, `verify`, `verify_essentiality`, `verify_growth_build`, `verify_tf_build`, `verify_morphology_build`, `run_tolerance_verification`) |
| `none` | 16 | nothing |
| `registry` | 71 | a family runner in `torchcell/verification/runners.py`, reached through one of its 12 family registries or the three morphology root constants |

A registry runner is called with its registry narrowed to the dataset under verification, so a
crash in one store stops at that store. The per-dataset L4 rules a runner adds still run,
because the runner reads the stores those rules compare against (Ohya for the yeast
containment rules, the record's pinned assembly for the bacterial ones). `run_expression` is
not narrowed: its L4 compares the three expression datasets' measured universes against each
other.

The module route's entry point, argument order and arm selector are recorded per dataset in
the script's `MODULE_ROUTES`, read off each module's signature and CLI `verify` subcommand,
never inferred at runtime. The arm selectors are the modules' own keys:
`ishii2007.DATASET_ROOTS`, `yunus2026.DATASETS`, the `Family` literals of `caglar2017` and
`menasalvas2025`, and the class itself for `schmidt2016_srm`. PR #850's
`build_dataset_lmdb.resolve_verifier` resolves a single-store subset of the same routes for
`--verify`; it refuses modules whose entry point needs a family, arm or name selector, which
this table covers.

Every route is read-only on `processed/` (the runners' readers open each LMDB
`readonly=True, lock=False`). The only bytes written are the
`preprocess/verification_report*.json` files each route writes by its own convention, in the
dev tree. `$DATA_ROOT/database/` was never touched and no store was rebuilt. Each dataset ran
in its own subprocess.

### What the two FAILs are

**`ffa_xue2025`, L4 `gene_containment_scmd_ohya2005` (0.769 < 0.9; missing `YLR071C`,
`YNL039W`, `YOR174W`).** There are two separate causes, and both change stored records:

- #886: the release's `TFC7` is stored as `YNL039W` (BDP1) in 46 records. `TFC7` is an
  alias of both `YNL039W` and `YOR110W` in `alias_to_systematic`, and is the standard name of
  `YOR110W`, but the loader returns `candidates[0]`. The same first-candidate code is in
  `dasilveira2014.py` and `sameith2015.py`. Measured on their stores: da Silveira's two
  ambiguous names (`YPK1`, `SLT2`) land on their standard ORFs by list order, and Sameith has
  none.
- #887: RGR1 (`YLR071C`), MED4 (`YOR174W`) and TFC7 are essential in the served
  `gene_essentiality_sgd` store, yet are stored as full `KanMxDeletionPerturbation`s in a
  haploid BY4741 chassis: 112 of 176 records. The rule is right, and the fix is an owner
  decision about which allele the in-house strains carry.

**`phage_rbtnseq_mutalik2020`, L3 `environment_perturbed` (29,392 records with no
environmental edit, 0 declared).** #888. These are no-phage controls the release runs on
purpose (the report's own `experiment_kind_census` passes, at 36,732 controls). The loader
landed on 2026-10-07, before #776 (`2e0bb89cd`, 2026-10-09) added the `expected_unperturbed`
declaration, so it never declares them. The gate's count is 7,340 smaller than the loader's
because it reads the two controls in a non-modal medium (plain LB: 3,667; solid LB +
kanamycin: 3,673) as edited. No stored record changes.
