## 2026.09.26 - Baseline analysis and the benchmark ladder

Objective: wall time of the 51-dataset CSV generation (28 h 15 min on job 2032, the
release 1.2 build) inside half of GilaHyper, 64 CPUs and 256 GB, with no OOM. Import is
17 min and is not the target.

Where job 2032 spent its 28 h, from the slurm log timestamps
(`experiments/tcdb-002-build-speed/results/build2032_per_adapter.csv`, regenerated by
`scripts/profile_build2032.py`):

| class | datasets | median records | hours |
|---|--:|--:|--:|
| small, under 50k records | 33 | 1,484 | 9.5 |
| mid, 50k to 5M | 16 | 410k | 9.4 |
| Costanzo dmf + dmi, 20.7M each | 2 | 20.7M | 9.4 |

W&B run for job 2032:

<https://wandb.ai/zhao-group/tcdb/runs/6etw9rur>

Findings that define the rounds:

- A dataset of 12 records took 1,003 s; the small class median is 772 s. Every adapter
  runs 17 to 25 methods and each method forks a pool, forks loader children per worker,
  opens the LMDB and tears it all down: about 30 s per method whatever the size.
- Every method re-traverses the whole dataset. Costanzo dmf ran 17 chunked passes over
  20.7M records at 10 to 20 min each.
- Per record, pydantic rehydration is 1.06 ms against 0.08 ms for the LMDB read
  (`scripts/record_cost.py` on the dev dmf_costanzo2016 LMDB, 2,000 records). The
  constant Environment is 0.45 ms of that and the constant reference 0.43 ms, and the
  reference is constructed twice in `transform_item`.
- sacct: job 2032 was allocated 48 CPUs under the memory floor and the container was
  capped to the 24 it asked for.
- W&B's system metrics saw only the parent process (2% CPU, 6 threads), so worker CPU
  and memory were invisible. Round 0 adds a cgroup sampler.

Benchmark ladder (`torchcell/knowledge_graphs/conf/kg_bench_ladder.yaml`): 5 small
(Zelezniak metabolite 95, SGD essentiality 1,329, Kuzmin 2018 smf 1,539, Cooper 4,313,
Smith 2006 12,747), 2 mid (Kuzmin 2020 tmi 301,798, Kuzmin 2018 dmf 410,399), Costanzo
dmf capped to 2M. Generation only, production container and mounts, wheel frozen at
submit (`scripts/submit_bench.sh` -> `scripts/gh_bench_generate.slurm`). Scored by
`scripts/bench_report.py` from the per-phase telemetry.

Round plan: r0 baseline (instrumented, unchanged code); r1 in-process path for datasets
up to 25k records; r2 cache validated constant sub-objects in `transform_item`; r3
single-pass node emission; r4 chunk size and worker count in the target box.

### r0 baseline

Job 2851, commit dad37766, 48 CPUs / 192 GB (the idle capacity at submit; the two
pending GPU pack jobs ahead in the FIFO were held for the 30 s it took to start, then
released). Results below when it finishes.

Correction: job 2851 ran `chunk_size: 4e5`, copied from `kg_small.yaml`, not the
production `1e5` from `kg_uncapped.yaml`. A 410k-record dataset then splits into 3
chunks and 3 of 43 workers do the work (DmfKuzmin2018 node methods took 3 to 5 min each
against about 70 s per method on job 2032). It is scored as a chunk-size arm. The ladder
config now carries the production adapter settings and an arm deviates only through
`KG_OVERRIDES` hydra overrides recorded in its `arm.tsv`.

Local verification before submitting, `SmfKuzmin2018Adapter` on the dev LMDB (1,539
records, 4 process workers, `scripts/test_inprocess_equivalence.py`): pool,
in-process, single-pass, and single-pass plus in-process all emit the same node id set
(sha 2d0382eef4a03ee3, 12,319 nodes) and edge id set (6a43a44263328f63, 13,855 edges).
Wall for the whole adapter locally: pool 15.6 s before r2, 8.3 s after r2, 2.8 s with
single-pass. Cached-constant `transform_item` on 2,000 dev records: dmf_costanzo2016
1.02 -> 0.16 ms per record, smf_kuzmin2018 1.35 -> 0.10 ms, `model_dump` byte-identical
(`scripts/test_validated_cache.py`).
