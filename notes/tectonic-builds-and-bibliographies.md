## 2026.09.01 - How Tectonic Builds Our PDFs, and Where Each Bibliography Comes From

Documented from the build files as they exist today: `notes-tex/common/Makefile.common`,
`paper/nature-biotech/Makefile`, `notes-tex/common/build_bib.py`,
`paper/nature-biotech/zotero_export_bib.py`, `scripts/lit_bib.py` /
`torchcell/literature/bib.py`, and `torchcell/literature/server.py`.

### Tectonic itself

- Both build systems resolve the engine the same way:
  `TECTONIC ?= $(shell command -v tectonic || echo /tmp/tectonic)`. An installed
  binary wins; `/tmp/tectonic` is the fallback for a machine where one was fetched
  by hand. Permanent install: `conda install -c conda-forge tectonic` (the Mac
  currently has Tectonic 0.16.9 at `/usr/local/bin/tectonic`, via brew).
- Why Tectonic: one binary, no TeX Live install, deterministic package fetching,
  and it honors `SOURCE_DATE_EPOCH` (see reproducibility below).
- Two quirks both Makefiles work around:
  - Tectonic does not honor `TEXINPUTS`, so shared style files (`tcdoc.sty`,
    `sn-nature.bst`) are symlinked into each notes-tex document directory at build
    time. The symlinks are gitignored and any build recreates them.
  - Logs are discarded by default, so notes-tex compiles pass `--keep-logs` (the
    `make check` gate reads the log) and `--synctex` (editor jump-to-source).
- Reproducible builds in BOTH systems: `SOURCE_DATE_EPOCH` is exported as the
  newest mtime among the build inputs. Without it hyperref writes a wall-clock
  `/CreationDate` and two builds of identical sources differ in sha256, which
  breaks `zotero_publish.py` (it versions review copies by content hash). The
  epoch is a real mtime, not a constant, so `\date{\today}` still reads as the
  date the text was last edited.

### notes-tex documents (`notes-tex/<slug>/`)

Each document directory has a thin Makefile that sets its Zotero collections and
does `include ../common/Makefile.common`. The document root and PDF are named for
the directory (`DOC ?= $(notdir $(CURDIR))`), never `main`.

- `make` -- `tectonic -X compile <slug>.tex --keep-logs --synctex --outdir .`,
  producing the draft view (status chips + provenance flags).
- `make clean-view` -- sed-swaps `\usepackage[draft]{tcdoc}` to `[clean]` and
  compiles `<slug>-clean.pdf` for sharing outside the group. `\external` and
  `\secondhand` flags deliberately survive the clean view.
- `make check` -- `common/check_doc.py`: formatting, provenance, and citation gate
  (fails on em-dashes, British spelling, `\cite` keys absent from the bib). Reads
  the last build's log rather than rebuilding.
- `make bib` / `make bibcheck` -- see bibliographies below.
- `make figures` -- re-exports any referenced draw.io sources from
  `notes/assets/drawio/` to `figures/NAME.pdf` (platform-aware: macOS uses the
  draw.io.app CLI, Linux the AppImage under xvfb). Verifies the output is newer
  than its source; refuses to run without an executable exporter.
- `make plots` -- converts matplotlib true-size SVGs from
  `notes/assets/images/<slug>/` to `figures/NAME.pdf` with rsvg-convert, at a
  measured zoom (it probes librsvg's unit interpretation first, because the
  true-size SVGs carry unitless 100-per-inch widths).
- `make watch` -- `tectonic -X watch`.

### The manuscript (`paper/nature-biotech/`)

- `make paper` -- builds the three views (`submission.pdf`, `editing.pdf`,
  `twocolumn.pdf`), each `tectonic -X compile <view>.tex` over the shared body
  (`content.tex` + `sections/*.tex`), then prints the word-count report.
- Hard figure gate: every view depends on `checkfigs` (`check-figures.sh`), which
  first re-exports any figure whose draw.io source is newer than its PDF, then
  refuses to compile while any figure exceeds 180x240 mm or is placed scaled.
  `make fig` force-re-renders every referenced figure regardless of timestamps.
- `Fig1-torchcell-overview` gets a `pdfcrop` crop-to-ink after export
  (`CROP_FIGS`): MathJax labels give draw.io's `--crop` a phantom bounding box.
- `editing.pdf` additionally depends on `wordcount.tex` (regenerated by
  `wordcount.py`) so the embedded per-section budget table always matches the
  compiled draft; submission/twocolumn define `\cb` as a no-op.
- `make publish` -- uploads `editing.pdf` as a hash-versioned review copy to the
  personal Zotero library under `torchcell / paper / nature-biotech` via
  `notes-tex/common/zotero_publish.py` (collection path derived from the
  directory). `publish-dry`, `publish-list`, `publish-submission` variants.
- `make flat` -- flattens to a single `submission-flat.tex` for Springer.
- Mac-only alternate path: MacTeX `latexmk` is installed and has been used to
  build `editing.pdf` directly (the `.fdb_latexmk` in the tree is from it). That
  path skips `checkfigs` and `SOURCE_DATE_EPOCH` entirely -- fine for a fast
  local iteration, but `make paper` is the canonical, gated build.

### Bibliographies -- three flows, all Zotero, none served from GilaHyper

| bib file | generator | Zotero access | scope | runs where |
|---|---|---|---|---|
| `paper/nature-biotech/references.bib` | `zotero_export_bib.py` | Better BibTeX LOCAL endpoint (`localhost:23119`) | group library (6582362) `paper` collection (`W46ATS7B`) ONLY | a machine with Zotero desktop + BBT open (the Mac) |
| `notes-tex/<slug>/references.bib` | `make bib` -> `common/build_bib.py` | Better BibTeX LOCAL endpoint | UNION of group + personal collections named for the document; loud citekey-conflict detection | same, Zotero desktop required |
| `notes/assets/bib/bib.bib` (Dendron/pandoc) | `scripts/lit_bib.py` (`torchcell/literature/bib.py`) | Zotero WEB API via pyzotero, headless | whole group library; add-only merge, never truncates | anywhere: the Mac, GilaHyper, cron |

- The paper flow is the publication guarantee: pinned citekeys, curated group
  collection only. The notes-tex union exists because technical notes cite more
  widely and much of that reading lands in the personal library first.
- The Dendron flow is the only headless one, and its entry keys are Zotero's
  native `citationKey` -- the same string that names each paper's mirror
  directory under `$DATA_ROOT/torchcell-library/<citation_key>/`, so a note's
  `@key` and the OCR markdown it cites line up with no mapping table.

### What tc-lit on GilaHyper does and does not do here

`tc-lit` (`torchcell/literature/server.py`, reached via `TC_LIT_URL`) streams
sha256-verified ARTIFACTS out of the `$DATA_ROOT/torchcell-library/` mirror:
`paper.md`, PDFs, SI, images, data. It serves no `.bib`, and nothing in any build
consumes `TC_LIT_URL` (verified by grep: the only reference is the server
itself). Its connection to the bibliographies is indirect and by-name only: the
mirror's directory names are the citation keys the bibs use.

### Expectation check (2026.09.01)

The one expectation that does NOT match reality: "use the bibliography from the
torchcell library served on GilaHyper." No bibliography is served from GilaHyper.
Both LaTeX bib flows require Zotero desktop + Better BibTeX running locally, so
`make bib` and the paper's bib regeneration only work on the Mac. If a
GilaHyper-served bib is wanted, the natural route is a `/bib` endpoint on tc-lit
backed by the Web-API export that `lit_bib.py` already does headless -- currently
unbuilt.

## 2026.09.02 - The `/bib` Endpoint Is Built: One Served Bibliography per Document

The gap in the expectation check above is closed. tc-lit now serves a **bibliography
store** ([[torchcell.literature.bib_store]]): `GET /bib` is a manifest of every served
`.bib` with its sha256, `GET /bib/<name>` streams one with `X-Artifact-SHA256`. The
store is `$DATA_ROOT/torchcell-library/_bib/`, exported nightly on GilaHyper by
[[scripts.lit_bib_store]] over the Zotero Web API (headless), and pulled on any machine
by [[scripts.lit_bib_pull]] or `make bib-pull`.

The table of bibliography flows gains a fourth row, and it is the only one that works
on every machine:

| bib file | generator | Zotero access | scope | runs where |
|---|---|---|---|---|
| `_bib/<name>.bib` served at `/bib/<name>` | `scripts/lit_bib_store.py` (nightly cron 03:45) | Zotero WEB API via pyzotero, headless | `paper` = group `W46ATS7B`; `<notes-tex slug>` = that Makefile's group + personal collections; `library` = group + personal `torchcell` tree | export on GilaHyper; pull anywhere with a tc-lit key |

Names are discovered from the repo (the paper's `DEFAULT_COLLECTION`, each notes-tex
Makefile's `ZOTERO_COLLECTION`/`ZOTERO_PERSONAL_COLLECTION`, the `lit_bib.py` union), so
adding a document that declares a collection adds a served bibliography on the next
export with no config edit.

How the machines get on the same page: a document's `references.bib` is pulled from the
store (`make bib-pull`), diffed, and committed. Both the Mac and GilaHyper then build
from the same pinned bytes, and the Better BibTeX route (`make bib`) becomes the
optional path rather than the only one. The two routes agree on citation keys (Zotero 7
native `citationKey`) and differ in field formatting, so the first pull of a document
that was last generated through BBT shows a formatting diff once.

First export: `paper` 24, `024-perturb-seq-costing` 42, `eqtl-data-model` 2, `library`
615 entries. Tests in `tests/torchcell/literature/test_bib_store.py`.

### State of the committed bibliographies vs Zotero (measured 2026.09.02)

The first export was diffed key-by-key against each committed `references.bib`, and the
Zotero collections behind the differences were inspected read-only (scratch scripts,
`pyzotero` on the Web API). Every committed file is behind Zotero, and pulling any of
them today would break its build on cited keys, so **none was pulled**. Curation is the
author's call; nothing was written to Zotero.

What the collections hold today:

- **`paper`**: 24 citable items. The four keys the manuscript cites but the collection no
  longer holds were in the collection at the last Better BibTeX export and are not now;
  the eleven new items were added since. `merzbacherAccuratePredictionGene2025` and
  `...2025a` are both present (a dup-twin).
- **`024-perturb-seq-costing`**: group `microbe-perturb-seq` 15 citable, personal
  `torchcell/torchcell-topics/microbe-perturb-seq` 42 citable, group a subset of personal,
  neither with sub-collections. The committed file was generated by `build_bib.py` from
  these same two collections, so the thirteen cited keys it holds were in the personal
  collection then and are not now.
- **`eqtl-data-model`**: the group twin `VNDH4NMX` is EMPTY. The personal collection the
  Makefile names, `4VNJWJAW`, is `torchcell/notes-tex/eqtl-data-model`, the document's
  PUBLISH collection (the report `volkWhatEQTLData2026` plus Boocock 2025), not a topic
  collection under `torchcell-topics/`; no `torchcell-topics/eqtl-data-model` exists.
  Seven of the eight cited references are not found in either library by title search.
  The committed file's own header says it was emitted by `zotero_add_ref.py
  --emit-bibtex` and hand-patched pending a Better BibTeX run, which matches: those
  seven entries exist only in the committed file. This document's bibliography cannot
  be regenerated from Zotero by either route until the items are in a collection.

So the store is the current truth of the collections, and the committed files are
snapshots of earlier curation. Getting on the same page is a curation pass per document
(re-add or re-pin the cited items, or drop the citations), after which `make bib-pull`
gives every machine the same bytes.
