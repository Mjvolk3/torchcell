### Why `aggregator=RecordAggregator` instead of `aggregator=None`

The design asks for `aggregator=None`. On main (v1.8.4) that path does not work, measured
offline on 2026.10.19 with a one-record raw LMDB in the scratchpad:

- `Neo4jCellDataset.process` copies `raw/lmdb` into `processed/lmdb` unchanged
  (`_copy_lmdb`), so the processed keys are `data_<i>` and each value is one JSON object.
- Every processed-store reader expects keys `<i>` and a JSON list per value:
  `_read_from_lmdb(0)` returned `None`, and `compute_phenotype_info` raised
  `TypeError: string indices must be integers, not 'str'`
  (`torchcell/data/neo4j_cell.py`, line 561). The real build would die there, after the
  whole raw fetch.
- The deduplicator alone has the same problem: it writes keys `<i>` but one object per
  value (`torchcell/data/deduplicate.py`); only the aggregator writes the list format.

`RecordAggregator` (defined in the script, nothing in `torchcell/` changed) keys every
record by the sha256 of its own JSON content, so every group is one record and the
processed store holds the raw records one per entry, in the list format. The build asserts
`processed entries == raw records`; two byte-identical served records would fail the build
rather than merge. Offline probe with 12 synthetic records: 12 raw, 12 processed,
`get(0)` reads a one-element list, `compute_phenotype_info` passes.

The underlying `aggregator=None` defect is a torchcell bug to fix separately
(hypothesis (untested): rekeying `data_<i>` to `<i>` and wrapping each value in a list in
the raw-to-processed copy is sufficient).

`Neo4jQueryRaw.extract_systematic_gene_names` assumes every genotype has a
`perturbations` list. A `SegregantGenotype` has none (it carries `cross`, `segregant_id`,
parents and blocks); in the dev census only Boocock 2025 and Nguessan 2025 have that
shape, so the failing record is presumably one of theirs (the log does not name the
record). Nothing was committed: `raw_043/raw/lmdb` is empty and the whole tree is 92 KB.

Not patched, per the stage-1 brief. Further segregant hazards on the same path, read from
the source and not run (hypothesis (untested)): `RawStageGrouping.prepare` reads
`experiment["genotype"]["perturbations"]` for its summary (KeyError), and the
`Perturbation` graph processor reads the perturbation list in `get`. A torchcell fix that
treats a genotype with no perturbation list as zero gene perturbations, or dropping the
two segregant datasets from this store, is the owner's call.

Findings from the rebuild (measured, not fixed here):

- **Duplicate label in `phenotype_types`.** `expression_log2_ratio` appears twice because
  two phenotype classes in the store carry that `label_name`. The Kemmeren sample stores
  12,338 values for a 6,169-gene label, which is every value twice. Hypothesis
  (untested): the same doubling applies to every `expression_log2_ratio` record
  (Kemmeren, Sameith, Nadal-Ribelles).
- **The perturbation-count index omits every segregant.**
  `compute_perturbation_count_index` logged
  `Error processing entry ...: 'perturbations'. Skipping this entry.` 82,467 times, which
  equals Boocock plus Nguessan. `perturbation_count_index.json` holds 91,150 of 173,617
  entries. This is the same missing-list read, at a site the stage 2 fix did not cover.
  It ran because a resumed build (raw stage skipped) computes the indices from the
  processed store instead of folding them from the raw stage.
- **Isolates mark thousands of genes perturbed.** The Caudal sample has `pert_mask` sum
  5,575 of 6,607 nodes, because every `sequence_variant` gene counts as perturbed. Of the
  5,672 distinct gene names, 97 are not graph nodes (pangenome ORFs).
