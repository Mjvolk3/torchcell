## Context

Sequence-level reference data has three homes today and none of them is a provenance record.

- The S288C R64-4-1 release sits at `$DATA_ROOT/data/sgd/genome/S288C_reference_genome_R64-4-1_20230830/` (9 files, 106 MB, uid 7474, hard-linked into the KG-build tree), fetched by `s288c.py:615-645` through `torch_geometric` `download_url` with no sha256 and the container deleted after extraction; no manifest exists for these files.
- The Peter 2018 1,011-isolate assets (4.2 GB, five files plus a derived member index) live under the literature key `torchcell-library/peterGenomeEvolution10112018/data/`, filed as a paper's data although two dataset loaders, the verification runner, and four experiment scripts read them as reference genomes; that key's manifest pins their sha256 but records `retrieval: None`, `source: None`, and still says `provenance_complete: true`.
- `torchcell-raw/` holds loader-consumed raw files but no genomes.
- Nothing backs up `data/sgd/genome`: `scripts/backup_mirrors_to_bulk.sh:25` lists only `torchcell-library` and `torchcell-raw`.

"Genomes are pointers" (id + source + sha256, sequence dereferenced at load), the stance fixed in the Caudal and plasmid-design notes, therefore has no place to point. Bloom stores `1011Assemblies.tar.gz::GENOMES_ASSEMBLED/<KEY>_<N>.re.fa` plus the tarball sha256; Caudal stores `sequence_sha256`; BY stores two prose sentinels. Every stored string is path-free, so a filesystem reorganization invalidates no LMDB, which is the window this work uses. The tier gives those pointers one on-disk target with a pydantic manifest, one code authority for resolving them, sha256 verification on every resolve, and a backup.

**Re-fetch state (measured 2026-09-14, this session; `REFETCH` is defined in Verification).** The S288C retrieval is reproduced, not pending: `curl -sSL http://sgd-archive.yeastgenome.org/sequence/S288C_reference/genome_releases/S288C_reference_genome_R64-4-1_20230830.tgz` gave 21,142,292 bytes, sha256 `987e7e324dee8e97368a27a34aa351537a4fa9342a43eaec82f2993486c48de1`, kept at `$REFETCH/sgd/S288C_reference_genome_R64-4-1_20230830.tgz`; `tar -xzf` plus gunzip of every `.gz` member yields exactly eight files, each matching the on-disk file by sha256: `gene_association_R64-4-1_20230830.sgd`, `NotFeature_R64-4-1_20230830.fasta`, `orf_coding_all_R64-4-1_20230830.fasta`, `orf_trans_all_R64-4-1_20230830.fasta`, `other_features_genomic_R64-4-1_20230830.fasta`, `rna_coding_R64-4-1_20230830.fasta`, `S288C_reference_sequence_R64-4-1_20230830.fsa`, `saccharomyces_cerevisiae_R64-4-1_20230830.gff`. The ninth on-disk file, `ncbi_genomic.gff`, is not in the tgz (written by `s288c_ncbi.py:394`). The Peter re-fetch from `http://1002genomes.u-strasbg.fr/files/` into `$REFETCH/peter/` is in progress: `allORFs_pangenome.fasta.gz`, `allReferenceGenesWithSNPsAndIndelsInferred.tar.gz`, `genesMatrix_CopyNumber.tab.gz`, and `genesMatrix_PresenceAbsence.tab.gz` are complete and match the library manifest sha256 (`sha256sum`, 2026-09-14); `1011Assemblies.tar.gz` (3,999,623,201 bytes) finished after the draft and matches too: sha256 `53540d095958ae8c32509c04485f0d2d0948069c7647f828698d611899a9b4da`, equal to the library manifest. ## Key Design Decisions

1. **Copy, never move, and no symlinks anywhere.** `cp -a` gives the tier michaelvolk-owned inodes with link count 1; the old S288C directory and the library `data/` stay untouched. The S288C files are hard-linked (link count 2) into `/scratch/projects/torchcell/database/data/sgd/genome/...` owned by uid 7474, so a move keeps a shared inode, and a compatibility symlink is what would create the rsync hazard (gotcha 5), the Caudal dangling-link `FileExistsError`, and a library manifest claiming files it no longer has. Disk cost is 4.2 GB against 1.3 T free on /scratch. "One standard place" is delivered by code authority, not filesystem uniqueness. Rejected: move plus symlink (memory `gilahyper-storage-tiers` precedent).

2. **A sibling `GenomeManifest` that reuses the per-file records.** `ArtifactRecord`, `RetrievalRecord`, `RetrievalMethod`, `ProcessingRecord`, and `sha256_file` from `torchcell/literature/manifest.py` are reused verbatim; the top-level literature `Manifest` is not, because it is paper-keyed (`citation_key` required, `doi`, `zotero_item_key`, `si_expected`) and SGD is not a paper. Roles are set explicitly by the deposit script, not by `_role_for` (L177), which infers paper roles from paths. `manifest.py` is not edited: `feat/kinetics-equilibrator-datasets` (ahead 50) adds `git_clone` to `RetrievalMethod` at L73 and would conflict; if a rebase ever touches it, keep enum additions at the end of the class.

3. **The registry is the sole path authority, with hard errors and no legacy fallback.** `resolve` raises `FileNotFoundError` naming the assembly set and the rsync command when the tier is absent, and `GenomeIntegrityError` on a sha256 mismatch. CLAUDE.md forbids fallbacks unless asked, and a logged-warning fallback to `data/sgd/genome` would keep Delta, IGB, and the Mac on unverified bytes indefinitely, which is the failure the tier ends. The cost is a one-time rsync of the 106 MB S288C set per machine (gotcha 8, follow-up 7).

4. **The S288C download path is removed, not kept as the no-tier branch.** `download_and_extract_genome_files`, `untar_tgz_file`, `gunzip_all_files_in_dir`, and the `osp.exists` guard go. With the registry as sole resolver there is no state in which an unpinned, container-deleting fetch should run; keeping it "for when the entry is missing" is decision 3's fallback under another name.

5. **`genome_root` keeps its meaning as the cache root; the ctor and pickle contract are untouched.** `SCerevisiaeGenome(genome_root, go_root, overwrite)` stays, `genome_root` remains a plain `str`, `data.db` is still created at `osp.join(genome_root, "data.db")` (`s288c.py:528`), and through `SCerevisiaeGraph.sgd_root` it remains the parent of `genes/` (6.5 GB) and `graph/` (3.9 GB). Only the four release-file paths move to the registry. `__reduce_ex__` (L590-613) pickles those three ctor args and `__attrs_post_init__` reruns on unpickle in every DDP worker; 312 call sites pass a root ending in `data/sgd/genome` and none passes an assembly id. Nothing that changes on construction may enter a manifest-pinned directory.

6. **`overwrite` default stays `True` in this PR.** With copy-not-move `data.db` never moves, so the overwrite race (memory `genome-overwrite-true-rebuild-race`, 2026-09-05) does not bear on the migration; flipping it changes behavior at 67 sites (18 bare, 49 positional) and needs a DDP-safe build-when-absent design (rank 0 builds, others wait), which is its own PR (follow-up 2). `runners._genome` and both loaders already pass `overwrite=False`.

7. **`#73` is not bundled; the `sgd.py` path fix is.** This PR's checkable invariant is "no stored record would change on rebuild"; `#73` (Caudal SACE_ header drop) changes what a fresh Caudal build stores, so bundling it makes the invariant unprovable. The `sgd.py:165` bug (`sgd/genome/genes` without `data/`, so its `gene_count < 100` check always fails and it re-downloads) is a path-authority bug with no stored-record consequence, one line, verified by asserting the corrected path exists.

8. **The `ReferenceGenome` field is deferred to the full-rebuild window.** `schema_deps.canonical()` (`schema_deps.py:116-120`) hashes `field::{name}::{annotation}::{default}`, so an additive defaulted field moves the closure of all 36 served datasets and `kg_manifest admit` blocks with a full-rebuild verdict; the field goes in the window already deferred with `#92`, `#143`, `#195` (before-next-kg-build). Meanwhile the registry plus `manifest.json` carry assembly and sha256 off-graph, and the Bloom BY sentinel `S288C_ASSEMBLY` (`bloom2019.py:158`) is mapped to `sgd_S288C_R64-4-1_20230830` in a registry-level constant so a later dereferencer resolves BY without touching stored records.

9. **Retrieval records are genuine or absent, never fabricated.** A `RetrievalRecord` is written only where the re-fetch reproduced the bytes (Context). S288C did: the SGD set gets `method=direct_url`, `retriever=torchcell.literature.retrieve.direct_url`, `params={url}`, the container sha256 `987e7e32...`, `retrieved_at=2026-09-14`; the tgz is deposited in the tier as the stored container, and each of the eight members carries a `ProcessingRecord` (tar + gunzip, `input_sha256` = the tgz sha256). Peter: all five files reproduced (Context) and get the same kind of record with `last_check` set, so the Peter set is `provenance_complete=True`. The rule stays for any future set: a file whose re-fetch fails or mismatches gets `retrieval=None`, the set `provenance_complete=False`, and the copy origin in `notes`, never in `source_url`. A sha256 mismatch on any file halts the migration; that is drift detection working, not a branch to code around. `provenance_complete` keeps the literature manifest's exact meaning; no new gap type.

10. **The library's Peter copy is retained and its manifest stays byte-identical.** The library mirror's contract is "the paper's released data per citation key"; the tier relates to it as the raw mirror does, a loader-facing copy cross-referenced by sha256. Whether to deprecate the library copy is a `#271` decision for the later pass.

11. **Assembly-set ids and a flat layout.** `torchcell-genomes/sgd_S288C_R64-4-1_20230830/` and `torchcell-genomes/peter2018_1011_assemblies/`, each `manifest.json` plus files, no subdirectories, so `resolve(assembly_set, filename)` is a join plus a manifest lookup. SGD membership is the eight tgz members listed in Context plus the tgz; `ncbi_genomic.gff` is excluded, so `s288c_ncbi.py` and `s288c_gb.py` keep the legacy path this pass (follow-up 5). The Peter set holds the five files plus `1011Assemblies.tar.gz.member_index.tsv` recorded as derived (`ProcessingRecord`, `processor=experiments.embeddings.compute_isolate_embeddings.build_assembly_member_index`, `input_sha256` = the tarball sha256); the flat layout preserves its cache-next-to-the-tar convention.

12. **Verify-on-resolve replaces the loaders' own hashing.** Bloom `process()` and Caudal `download()` already hash the 4 GB tarball once; `resolve(verify=True)` becomes that pass rather than a second one. The S288C cost (106 MB per `SCerevisiaeGenome` construction, repeated in every DDP worker because `__attrs_post_init__` reruns on unpickle) is unmeasured; hypothesis (untested): well under a second next to the FASTA parsing already done. The implementer measures it once (verification step 7) and records the number in the s288c note; if material, `verify` stays on and the number is reported rather than the default flipped, and no cache is added before the number exists.

## Approach

**Registry API.** `torchcell/sequence/genome/registry.py` imports only `torchcell.literature.manifest` (bottom of the import graph). `genomes_root(data_root=None) -> str` reads `DATA_ROOT` through `load_dotenv` when `None`, matching every loader's `_data_root`. `load_genome_manifest(assembly_set) -> GenomeManifest` validates `<root>/<assembly_set>/manifest.json`. `resolve(assembly_set, filename, *, verify=True) -> str` returns an absolute path after checking the manifest entry exists and, when `verify`, that `sha256_file(path)` equals the recorded hash; a missing tier, set, or file raises `FileNotFoundError` whose message includes `rsync -a gilahyper:$DATA_ROOT/torchcell-genomes/<set>/ $DATA_ROOT/torchcell-genomes/<set>/`; a hash mismatch raises `GenomeIntegrityError`. `verify_assembly_set(assembly_set)` walks every manifest entry for the backup and bit-rot check. `deposit_assembly_set(...)` writes a manifest from explicit `ArtifactRecord`s and refuses an existing `manifest.json`; only the migration script calls it. A constant maps the Bloom sentinel `S288C_ASSEMBLY` to `sgd_S288C_R64-4-1_20230830`.

```python
class GenomeManifest(BaseModel):
    version: int = 1
    assembly_set: str          # directory name under torchcell-genomes/
    organism: str
    strain_or_population: str  # "S288C" | "1,011 isolates"
    source: str                # "SGD" | "Peter et al. 2018"
    release: str               # "R64-4-1_20230830" | "2018"
    citation_key: str | None
    source_url: str | None     # only when the retrieval is genuine
    files: list[ArtifactRecord]
    provenance_complete: bool
    created_at: datetime
    notes: str | None
```

**Migration script.** `scripts/migrate_genomes_tier.py` is the committed record of the deposit; `notes/scripts.migrate_genomes_tier.md` holds its printed output. It takes `--refetch-dir` and fetches a file through the `direct_url` retriever only when that file is absent there, so this run points at `$REFETCH` and reuses the bytes already fetched while a fresh machine running the same script performs a real fetch. Run by hand on GilaHyper, once, in this order: (a) sha256 `$REFETCH/sgd/S288C_reference_genome_R64-4-1_20230830.tgz` (must equal `987e7e32...`), extract and gunzip into a temp dir, print `member | on-disk sha256 | fetched sha256 | match` against `data/sgd/genome/S288C_reference_genome_R64-4-1_20230830/`, and halt on anything other than eight matches; (b) sha256 the five Peter files in `$REFETCH/peter/` against the library manifest, print the match/miss table, treat an incomplete or mismatched tarball as a miss, never retry in a loop; (c) create the two tier directories, `cp -a` the sources plus the tgz, `sha256sum` every tier file against its source, print `stat -c '%h %U'` and `du -sh`; (d) `deposit_assembly_set` for both sets with decision 9's records, then `verify_assembly_set` for both. The script never rebuilds `data.db`, writes into the old S288C directory, or touches the library key.

**Loader changes.** `s288c.py`: a class constant `ASSEMBLY_SET = "sgd_S288C_R64-4-1_20230830"`; `__attrs_post_init__` sets the four `_*_path` attributes from `resolve(ASSEMBLY_SET, <filename>)` instead of joining under `genome_root`; the three download methods and the `osp.exists` guard are deleted; `genome_version` and everything from `data.db` onward are unchanged. `hoepfner2014.py`, `hillenmeyer2008.py`, `runners.py`: the FASTA tuples become filenames resolved at use (`_sgd_gene_set`, L727/L789/L788); `runners._genome` keeps `overwrite=False`; the Bloom spec's `assembly_index` value becomes a `resolve` call at L1584. `bloom2019.py`: `process()` L990 reads the index through `resolve("peter2018_1011_assemblies", ASSEMBLY_INDEX)`, and an assertion at first use checks the manifest's tarball sha256 equals `ASSEMBLY_TAR_SHA256`, so the stored-record invariant is a checked fact; `PETER_DIR_REL` is deleted. `caudal2024.py`: the three `download()` sources at L262-264 and `SGD_FSA_REL` become `resolve` calls; the symlink-into-`raw_dir` mechanics and `REFGENE_TAR_SHA256` stay. `sgd.py:165`: insert the `data/` segment.

**Infrastructure.** `backup_mirrors_to_bulk.sh`: `MIRRORS=(torchcell-library torchcell-raw torchcell-genomes)` and a header line naming the tier. Five GilaHyper slurm scripts: `-v /scratch/projects/torchcell-scratch/torchcell-genomes:/var/lib/neo4j/torchcell-genomes:ro`, which places the tier under the container's `DATA_ROOT=/var/lib/neo4j` so `genomes_root` finds it unchanged. `.gitignore`: three lines.

**Execution order.** Disk first (migration steps a-d, then the backup edit and a by-hand run), then code (registry and tests, `s288c.py`, the three verification-side files, the two loaders, infrastructure and `sgd.py`), then the `admit` re-check against the baseline saved before any edit, then notes, then `/stage`, `/commit`, PR, `/enqueue-merge`. The PR body states three things explicitly: the container mount is untested, each other machine needs the S288C set rsynced before pulling, and the old S288C copy is deprecated in a later pass.

**Out of scope.** The `ReferenceGenome` field; the `overwrite` default; `#73`; the experiments scripts and the 43 `data/sgd/genome_{rank}` sites; `s288c_ncbi.py` / `s288c_gb.py`; `database/build/build_linux-arm.sh`, `database/build/build_openstack.sh`, `database/scripts/import_database_openstack.sh`; any edit to the library key or `torchcell/literature/manifest.py`; any deletion or deprecation on disk.

## Gotchas

1. **The S288C release files are hard-linked into the uid-7474 build tree.** Link count 2, twin inode at `/scratch/projects/torchcell/database/data/sgd/genome/...`; `$DATA_ROOT/database/data/sgd/` is permission-denied, so a third link is unknown. Sidestep: `cp -a` only; after the copy, `stat -c '%h %U'` on every tier file must print `1 michaelvolk`. Never write into the old directory.

2. **`genome_root` conflates four things; only the release files move.** `data.db` (rebuilt on every `overwrite=True` construction), `genes/`, `go/`, `graph/`, `yeast-GEM.xlsx` all hang off `genome_root` or `sgd_root` (`graph/graph.py:364`). Sidestep: the registry returns file paths, never a root; `data.db*` never enters the tier, and the deposit script writes explicit records rather than walking a directory.

3. **Three 027 jobs (1838, 1839, 1840) hold `data.db` open.** Any `SCerevisiaeGenome()` with the default `overwrite=True` runs `gffutils.create_db(force=True)` on that file, and `GffutilsConnectionManager.get_connection` raises `FileNotFoundError` if the file is momentarily absent (`sequence/db_connection.py:94`). Sidestep: every construction during this work passes `overwrite=False`; `test_s288c.py` (fixture at L28-33 uses the default) is not run while those jobs are up, and the PR says so. Check `squeue -u michaelvolk` before any smoke run.

4. **About 90 hard-coded `data/sgd/genome` sites.** Core sites (`dataloading_lmdb.py:27`, `create_kg.py:119-133`, `build_dataset_lmdb.py:69-78`, `neo4j_cell.py` x5, tests) pass a root, not a release path, and keep working because `genome_root` semantics are unchanged. Had the download path survived, any un-migrated reader of the release path would re-fetch unpinned bytes; the grep in verification step 10 must come back clean.

5. **`rsync -a` copies symlinks as symlinks and never deletes.** A symlink left in the library key would replace the real 4 GB file in `/bulk/torchcell-library/.../data/` with a dangling link at the next Sunday run. Sidestep: no symlinks (decision 1); `--dry-run` first and read the itemized output for `L` entries. The cron line runs from the primary checkout on `main`, so the `MIRRORS` change takes effect only after landing.

6. **The library manifest is served by tc-lit and nothing validates it against disk.** `/keys/{ck}/files` returns the manifest list as-is (`literature/server.py:304-316`); a malformed edit is an HTTP 500 for the whole key; a `backfill.build_manifest` re-run walks disk (`manifest.py:233,256`) and would silently drop entries for missing files. Sidestep: the key's `data/` and `manifest.json` are not touched (decision 10).

7. **Container mounts cannot be exercised until the next build.** `gilahyper_build-slurm_docker.slurm:55-67` mounts `$(pwd)/database/data/sgd` and sets `DATA_ROOT=/var/lib/neo4j` (L122); `first_build`, `uncapped_build`, `increment_kg` mount only `database/data`, `data/torchcell`, and the dev LMDB (`increment:160-161`). Sidestep: add the read-only mount to all five, `bash -n` each, state "untested until the next increment" in the PR; the first `increment_kg` run after landing is the real test.

8. **Other machines have the genome only at the legacy path.** With no fallback (decision 3), Delta, IGB, and the Mac fail at `resolve` until the tier is seeded; on the Mac `DATA_ROOT` is the repo root, so the tier lands inside the checkout. Sidestep: the `.gitignore` lines in this PR; the rsync of the 106 MB S288C set precedes pulling this change on each machine (follow-up 7); the Peter set is needed only where Bloom or Caudal build.

9. **pydantic and gffutils versions differ across machines.** pydantic: requirements `>=2.8.2`, installed 2.12.3, `igb_delta_match_req.txt` pins 2.5.2; 2.13 changed `serialize_as_any` and `RootModel.model_copy` semantics. gffutils: installed 0.13, requirements `>=0.12`, IGB/Delta pin 0.12; 0.14 converts `pathlib.Path` via `os.fspath` and refactors attribute parsing. Sidestep: `str` paths and plain `BaseModel` fields, `model_dump_json(indent=2)`, hash files never the JSON text; pass `os.fspath` at the `create_db` boundary; stay `<0.14` until the resolver tests re-run under it; a `data.db` sha256 never goes in a manifest.
