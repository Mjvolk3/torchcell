## 2026.10.23 - The experiment, its number, and the first query

**What 046 is for.** The 031 inductive-fold program predicts betaxanthin production (Cachera 2023) in single-deletion strains the model never saw, scored as the fold average over five inductive folds with the Merzbacher pin (fold 0) beside it and the top-k call against Flux Cone Learning. Its bar is the GO rank-4 recipe w618 (fold average 0.228, pin 0.259 at 18 seeds). The owner (2026-10-22) wants knockout expression (Kemmeren 2014) and knockout proteome (Messner 2023) to enter that program inductively, as co-targets read off the gene nodes with one readout shared across nodes, never as per-strain inputs, since the panels cover a third (Kemmeren) to nine tenths (Messner) of the betaxanthin strains and a model that reads a strain's measured omics can only serve the measured strains.

**Why a new query rather than the side table.** The 2026-10-23 co-target store (`experiments/031-betaxanthin-module/scripts/build_omics_cotarget_store.py` on `feat/kinetics-equilibrator-datasets`) joined the two panels to the betaxanthin strains by deleted-gene name outside the graph, averaged the 146 ORFs Messner measured more than once, and supervised only strains the betaxanthin screen also had. The owner's answer: adding data means another query. One served dataset over Cachera, Mulleder, Kemmeren and Messner makes the omics phenotypes of records, keeps every replicate as its own record, admits the omics-only strains (deletions Cachera never screened) as samples, and defines the training set by a `.cql` file and a pinned build like every other 031 input. The 031 trainer lives on a branch 1,562 commits behind `main` that cannot read a store built under the current schema ([[031-worktree-predates-omics-store-schema]]), so 046 is built on `main` beside 043, and the trainer side is a separate step.

**The number.** 044 (organism similarity) is the highest experiment folder on `main`; 045 is held by the plan worktree `plan/045-trigenic-profile-inference` (branch name and an untracked plan note, no folder yet); nothing references 046. Worktree `exp/046-betaxanthin-omics-cotarget` from `origin/main` at 0e98a5f2a.

**The query.** `queries/betaxanthin_omics_046.cql`, written by `scripts/generate_046_cql.py`: four `UNION ALL` blocks (Cachera and Mulleder at graph level `metabolism`, Kemmeren and Messner at `node`), property-shaped RETURN, `ORDER BY e.id`, one partition marker per block. KG 4.0 release 2026.10.17-4295f7ca serves 4,759 / 4,678 / 1,484 / 4,699 experiments. The first draft used the `fig6_build` perturbation clause (every deletion names a gene in `$gene_set`, at least one deletion, non-deletion perturbations pass, which is what keeps the Btx cassette additions).

**First build (job 6154, cancelled; store moved to `/scratch/projects/torchcell-deprecated/2026-10-23_092046__raw_046`).** The raw stage took two minutes with four fetch workers and returned 11,885 records: Mulleder 4,678, Kemmeren 1,482, Messner 4,624 (the same two gene-set drops 043 saw) and **Cachera 1,101 of 4,759**. The 1,101 are the strains whose released `gene` cell is a systematic name and sit on the placed KanMX leaf; the other 3,658 release a gene symbol (`ADE2`) and, since PR #1085 (#1045, "every released name stored as released"), sit on `ReleasedIdentifierPerturbation` with `perturbation_type` `released_identifier`, `released_kind` `deletion` and `systematic_gene_name` equal to the symbol. They fail `ENDS WITH 'deletion'` and would fail `IN $gene_set` too. The 031 program's `fig6_pigment_transfer` raw store (old loader, resolved at load time) holds 4,669 Cachera records. The supported query `torchcell/knowledge_graphs/queries/amino_acid_betaxanthin.cql` carries the same clause and so returns the same 1,101 against KG 4.0.

**Consequence for the downstream.** The `Perturbation` graph processor maps `systematic_gene_name` to a node by exact match in `cell_graph["gene"].node_ids`, so a symbol-named record would come out with NO perturbed gene and no error. Resolution of the released symbol to its R64 ORF is the downstream step the loader deliberately left out (`torchcell/datasets/gene_alias_resolution.py`, `resolve_gene_name_strict`: a live name or a single-candidate alias resolves, an ambiguous alias needs a pin, anything else is a typed refusal). 046 therefore needs (1) a query clause that admits a released-identifier perturbation whose `released_kind` is `deletion` without the gene-set test, and (2) a resolving graph processor at read time that reports refusals rather than dropping records. Count query on the served Cachera perturbations: slurm job 6155.

### The rebuild with the extended clause and the resolving processor (job 6156)

Served count query (job 6155) over Cachera's 23,795 perturbation nodes: 19,036 `gene_addition`, 3,592 `released_identifier`, 1,167 `kanmx_deletion`; the node carries `perturbation_type`, `systematic_gene_name`, `perturbed_gene_name`, `host_genome`, `description`, `id`, `preferred_id` and no `released_kind`, so the type is the only thing a query can test. The clause now admits a `released_identifier` perturbation as a deletion without the gene-set test (all three loaders that write the leaf in this query write released kind deletion), and `scripts/resolving_perturbation_046.py` resolves the symbol at read time: strict (live name or a single candidate), then the SGD standard-name rule for an ambiguous alias with exactly one standard-name owner, else a typed refusal listed on the record under `unresolved_perturbations`.

15,477 records, raw = processed, 2.8 GB a stage, 7.7 min build with four fetch workers, 18.5 GB peak RSS; store `$DATA_ROOT/data/torchcell/experiments/046-betaxanthin-omics-cotarget/raw_046`, census `results/build_046_store_census.json`. Resolution over Cachera's released names: 3,511 strict, 75 by the standard-name rule, 6 refused (`AAD6`, `CRS5`, `FLO8`, `YLR287-A` not in R64; `PPA1` and `FEN1` ambiguous with no single standard-name owner), so 4,687 of 4,693 Cachera records have their deletion on a gene node and 6 carry an unresolved deletion for a trainer to exclude explicitly. Mulleder, Kemmeren and Messner perturbations are all gene nodes already. The 66 + 2 + 75 records the clause drops are deletions of ORFs the cell graph has no node for (dubious or retired ORFs); the gate is at query time, as in 043 and `fig6_build`, which is a modeling-time gate and not a loader one.

Two things the first census exposed, fixed before the census rerun: the processor resolved every non-node name, so Cachera's heterologous cassette additions `CYP76AD1` and `DOD` were listed as refused; it now resolves deletion-kind perturbations only. And the stock processor maps the feedback-resistant `ARO4` / `ARO7` alleles (gene additions with yeast systematic names) into `perturbation_indices` beside the deletion, so a Cachera record has three perturbed indices; this is the stock behavior `fig6_build` trained under and is left as is here, noted for the trainer design.
