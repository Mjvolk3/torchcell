## 2026.10.15 - Lane W: what the environment-response identity sites cost, measured

Lane R, deriving verification's perturbation families ([[torchcell.verification.perturbation_families]], PR #1122), found that `environment_response._genotype_signature._identity` names 17 discriminator fields by hand while the genotype leaves declare far more, that the identity sites disagree with each other, and that classifying the unread fields would move L1 duplicate accounting on every store in the family. It stopped there. This lane answers the question that decides whether any of it is urgent: **are any stored records wrong today?**

Short answer: **on the genotype axis, no -- zero records on all 16 stores, and the 74 unread fields cannot change a single row.** The measurement that proves it also found a different projection in the same rule that *is* wrong: the condition signature on the environment axis could not tell an aerobic record from an anaerobic one, and 9,671 of yeastphenome's 14,508 declared duplicate pairs are exactly that. That is fixed here.

Numbers below are regenerated by `experiments/database/scripts/environment_response_identity_outcomes.py` (`--field-table` for the field classification, `--dataset <name>` for a store), results in `experiments/database/results/environment_response_identity_fields.json` and `environment_response_identity_outcomes.json`. Every store was read **read-only** from the dev tree `/scratch/projects/torchcell-scratch/data/torchcell/`.

### The identity sites, and how they diverge

Verification holds **six** L1 uniqueness keys over the genotype, not three. Three read fields beyond `GenePerturbation`'s five, and those three are lane R's "three sites"; the other three read the bare systematic name or a shared `strain_id`.

| Site | What the strain key is | Beyond-base fields it reads |
|---|---|---|
| `environment_response._genotype_signature._identity` | sorted perturbation identities, background excluded | 15: `perturbation_type`, `crispr` (guide, pool), `donor_sequence`, `construction` (accession, lab, batch, plate, well), `collection`, `tag`, `terminus`, `degron`, `cassette`, `insertion_site`, `strain_label`, `released_kind`, `released_gene_id`, `allele_name`, `constructed_orf` |
| `fitness._genotype_signature._identity` | sorted perturbation identities | 5: `perturbation_type`, `crispr`, `strain_id`, `allele_name`, `released_gene_id` |
| `metabolite._genotype_signature` | sorted identities, `gene_addition` excluded | 3: `perturbation_type`, `variant`, `construct_name` |
| `bacterial_morphology._l1_pair_uniqueness` | the base triple, plus the WHOLE stored environment | 1: `perturbation_type` |
| `visual_score._l1_orf_uniqueness`, `protein._l1_orf_uniqueness` | the set of deleted systematic names | none |
| `rnaseq._l1_strain_uniqueness` | the shared `strain_id`, plus the whole environment | none (reads `strain_id` off the record) |

The three divergences that matter, in my own reading of the source:

1. `fitness` keys on `strain_id`; `environment_response` does not.
2. `environment_response` keys on `collection` and `construction`; `fitness` does not.
3. `metabolite` keys on `variant` and `construct_name`; neither of the others does, and it excludes `gene_addition` perturbations from the key entirely.

A fourth divergence is on the ENVIRONMENT axis and is the one that turned out to cost something: `environment_response._condition_signature` and `fitness._environment_signature` read seven and six hand-picked environment fields, `bacterial_morphology` and `rnaseq` key on the whole stored environment, and `environment_identity` in `torchcell/datamodels/identity.py` -- the projection that decides whether two records share ONE environment node in the served graph -- reads a seventh set. `environment_response` reads `dilution_rate_per_hour` and `fitness` does not; neither read `aerobicity`, which the served identity does.

### Are any stored records wrong today? The bracketing argument

An L1 uniqueness key that reads MORE fields can only split a group, never merge two. So for any store, re-keying under the WHOLE stored record brackets every possible field classification: whatever the 74 unread fields turn out to mean, the duplicate count after classifying them lies between the count under the key as shipped and the count under the whole dump. Three keys per store therefore settle the question without arguing about any field:

- `head` -- the seven-element condition signature plus the shipped strain signature, which is the rule as it stood before this lane.
- `genotype_full` -- the same key with the WHOLE stored perturbation dump as the strain, so no stored genotype field can merge two records.
- `environment_full` -- the same key with the WHOLE stored environment as the condition.

`head - genotype_full` is then exactly the number of records that collapse under the shipped key although some unread genotype field distinguishes them, and `head - environment_full` is the same number on the environment axis. `genotype_full` equals `head` on every store, including both stores that collapse anything at all: **not one of the 9,602,177 records re-keyed here is distinguished by a genotype field no identity site reads.** The 74 unread fields are therefore unable to change a single L1 row today, whatever each of them means. Two stores show the read fields doing real work in the other direction (`genotype_base` above `head`): `crispri_chemgen_smith2016` 13,943 records (13,358 separated by the guide spacer, 305 by the library pool, measured by dropping one field at a time) and `crispr_magic_lian2019` 221,055, plus `env_chemgen_hillenmeyer2008_het` 30,478 and `_hom` 5,039 (`collection` and `construction`). Those are the documented #507 and Smith 2016 cases, and they are why the key reads what it reads.

`env_chemgen_hoepfner2014` is the one store not re-keyed end to end here: its shipped report already reads `30308574 unique (study, strain, condition) records, one each`, 0 duplicated, and a key that reads more fields cannot raise a count that is already 0. Its genotype-axis and environment-axis numbers are 0 by that monotonicity, not by a fresh pass.

### The defect the measurement did find: the condition signature could not see oxygen

`environment.aerobicity` holds `aerobic` or `anaerobic` as a stated value, `ENVIRONMENT_IDENTITY_FIELDS` reads it, and the seven-element condition signature did not. On `yeastphenome` that is 9,671 of the 14,508 pairs the rule declared duplicate: one ORF, one screen, one medium, an aerobic record and an anaerobic one, counted as a repeat of each other. A second blind field in the same store is `media.state`: a liquid and a solid medium both named `SC`, both with an empty component list, shared one signature (it collapsed no record pair, because no strain was screened in both).

Three consequences, in the order they matter:

1. **No stored record is wrong, and the served graph is right.** Both records are stored, nothing is dropped, and `environment_identity` reads `aerobicity`, so the aerobic and the anaerobic environment are already two environment nodes.
2. **The L1 row was wrong, and its declared allowance was 3x too large.** `_pair_uniqueness_result` passes only when the observed duplicate count equals the declared one, so `expected_duplicated_pairs: 14508` was absorbing 9,671 distinct conditions and would have absorbed any true duplicate up to that number.
3. **A loader asked to "aggregate the declared duplicates" would have destroyed 9,671 measurements.** That is the path by which a verification-only defect becomes data loss, and it is the reason this did not wait.

### The projection, and why a refinement rather than a replacement

`_condition_signature` now ends with `_stored_identity_projection(env)`: every field named by `ENVIRONMENT_IDENTITY_FIELDS` and `ENVIRONMENT_OPTIONAL_IDENTITY_FIELDS`, with each sub-object projected onto its own identity tuple (`MEDIA_IDENTITY_FIELDS`, `MEDIA_COMPONENT_IDENTITY_FIELDS`, `TEMPERATURE_IDENTITY_FIELDS`, `CULTURE_FORMAT_IDENTITY_FIELDS`, `PRE_CULTURE_IDENTITY_FIELDS`, the union of the five environment-perturbation tuples, and a compound onto its identifiers plus its name). The field names are imported from `identity.py` rather than re-listed, so a field added there fails `test_condition_signature_reads_every_served_identity_field` until this rule reads it.

It is a refinement of the shipped signature, not a replacement of it by the served identity, and that is a measured choice. Keying the condition on `environment_identity` itself would also MERGE groups the shipped signature separates, because that projection drops a medium's `name` and normalizes a compound to its first identifier:

| Store | Served identities reached from several stored environments | What those environments differ in |
|---|---|---|
| `yeastphenome` | 2 (covering 6 and 2 environments) | `media.name` only: `SC` with `SC - Ade`, `- Arg`, `- Lys`, `- Met`, `- Trp`; and `SC` with `SC, HEPES [25 mM]` |
| `env_chemgen_wildenhain2015` | 3 (2 environments each) | one substance released under two names and two PubChem CIDs: molsidomine, cisplatin, pralidoxime (E and Z) |

Those pairs need a per-case judgment about compound and medium identity, which is not this lane's to make, so the refinement keeps the head elements (the medium's name among them) and can only split. Measured consequence of that choice: every store's duplicate count is pinned between `environment_full` and `head`, and since those two agree on 15 of 16 stores, the refined rule reports exactly what the shipped rule reported everywhere except `yeastphenome`, where it reports the floor, 4,837.

### What landed

1. `_stored_identity_projection` in `torchcell/verification/environment_response.py`, appended to `_condition_signature`.
2. `expected_duplicated_pairs` for `yeastphenome` in `ENVIRONMENT_RESPONSE_DATASETS`: 14508 -> **4837**, with the measurement in the comment. Re-keyed on the dev store after the change: 519,845 unique triples, 4,837 duplicated, equal to the declared count, so L1 passes.
3. Three tests in `tests/torchcell/verification/test_environment_response.py`, each verified to FAIL on the unfixed function: `..._separates_an_anaerobic_record_from_an_aerobic_one`, `..._separates_a_solid_medium_from_a_liquid_one`, and `..._reads_every_served_identity_field`, whose failing assertion is `assert unread == []` with the left side reading `['media', 'temperature', 'perturbations', 'aerobicity', 'culture_format', 'pre_culture', 'auxotroph_supplements']`.

Cost, measured on the family's largest store: the real streaming verifier costs **779 us per record** on a 30,000-record slice of `env_chemgen_hoepfner2014` (6.6 h extrapolated over its 30.3M records), and the projection adds **55 us**, so **+7%**. Projecting each sub-object onto its identity tuple instead of dumping it whole is part of what keeps it there: Hoepfner's stored environment is 13.5 kB of JSON, 10 kB of which is the bench provenance of its medium, culture format and pre-culture, and encoding all of it cost 62 us.

Two other consumers of the signature were checked rather than assumed. `natural_isolate_response` MATCHES a constructed condition signature against the stored one, which a refinement could break: all **33,985 records of `isolate_growth_peter2018` still match one of the 35 constructed conditions, 0 unmatched**. `tong2020`'s extra `pair_uniqueness_with_environment_perturbations` row asserts 0 duplicates, and a finer key cannot raise a count that is 0, so it holds by the same monotonicity. Test suites: `tests/torchcell/verification` plus `tests/torchcell/adapters` 1,623 passed, `tests/torchcell/datamodels` 2,225 passed, `tests/torchcell/datasets/scerevisiae` 1,679 passed, and the three E. coli loader suites that key on this signature 202 passed.

No schema symbol changes, no stored record changes, no rebuild: this is a verification rule and a registry constant.

### Verdict

**Fix before the KG 4.0 build, and the fix is this one:** the genotype half of lane R's finding changes nothing on any of the 16 stores and is a code-quality cleanup for after the build, while the environment half mis-reports 9,671 record pairs on a store the build verifies and declares an allowance that hides every true duplicate under it, at the cost of one verification rule, one registry integer and no rebuild.

### Handed on, measured but not changed here

1. **`yeastphenome` states a medium's composition only in its `name`.** `SC - Ade`, `- Arg`, `- Lys`, `- Met`, `- Trp` (4,195 records each), `SC (-C)` and `SC, Glycerol [2%]` and `SC, HEPES [25 mM]` all carry `components: []` and `dropouts: []`, so the served environment identity cannot tell a dropout medium from plain `SC` (212,402 records) and puts them on one environment node. One fact, one field (constitution principle 5) puts the dropout in `Media.dropouts` and the carbon source and the buffer in `Media.components`. That is a loader change sourced from the YeastPhenome release, and it changes stored records, so it is a dataset lane with a rebuild of that store -- cheap before the 4.0 build, a second full rebuild after it.
2. **Three of the 16 dev stores cannot be unpickled on `ontology-unify`.** `load_records` on `env_chemgen_mota2024`, `crispri_mormino2022` and `env_chemgen_auesukaree2009` raises `AttributeError: Can't get attribute 'ReleasedGeneKind'`, the enum P3 renamed to `ReleasedKind`. The family verification run would crash on them, and so would any build step reading those dev LMDBs. Covered by the KG 4.0 full rebuild that [[database.kg-4-pre-build-verification]] already names; the measurement script reads them through a reported read-only alias map so the stale store is named rather than skipped.
3. **The family verifier cannot run end to end on any of the 16 dev stores on this branch.** `verify_environment_response_entry` raises before it reads a record: `ValueError: genome reference 'Saccharomyces cerevisiae' 'BY4741' pins no assembly set (gapped fields: []); no gene universe can be read for it`, and all 16 fail the same way under their own strain names. That is P2's assembly pin against stores built before it, so the end-to-end proof of the new L1 row has to wait for the dev-store rebuild; the re-keying above is what is measurable today, and it is the number the row reports. Pre-existing and independent of this change (the raise is in `_reference_assembly_set`).
4. **`Environment.growth_phase` is in no identity projection**, neither the served one nor any verifier's. Exponential and stationary phase are different conditions, so this looks like a gap in `ENVIRONMENT_IDENTITY_FIELDS` itself. Not urgent on the one store I measured it on: `growth_phase` is `None` on all 524,682 yeastphenome records.
5. **`fitness._environment_signature` has the same blind spots** (`aerobicity`, and it does not read `dilution_rate_per_hour` either) and `fitness._l1_pair_uniqueness` has no declared-duplicate allowance, so a blind field there can only make L1 FAIL, never pass quietly. I did not re-run the fitness family, so this is unmeasured on those stores rather than measured null.
6. **`bacterial_morphology`, `visual_score`, `protein` and `rnaseq` key the strain on less** than any of the three sites above (the base triple, or the bare systematic name, or a shared `strain_id`). Making the six keys one derived projection is the cleanup lane R's note is really asking for, and nothing measured here is blocked on it.
